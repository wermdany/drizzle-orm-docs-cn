# Drizzle 关系基础

在数据库的世界里，尤其是关系型数据库中，关系的概念绝对是基础。
可以把“关系”理解为不同数据片段之间的连接和关联。就像现实生活中，
人与人之间有各种关系，或者物品与类别相关联一样，数据库使用关系来建模不同
类型的信息如何相互连接与协作。

### 范式化
规范化是组织数据库中数据的过程，目的是减少冗余（重复）并提升数据完整性
（准确性和一致性）。可以把它想象成整理一个凌乱的文件柜。与其把所有纸张
塞进一个文件夹，不如将它们整理到逻辑清晰的文件夹和类别中，让一切更容易查找和管理。

<Callout collapsed="为什么规范化很重要？">
- **减少数据冗余**：想象一下每次客户下订单时都存储他们的地址。如果地址变了，你就不得不在多个地方更新它！规范化帮助你把信息存在一个地方，并从其它地方引用它，从而最大程度减少重复。
- **提升数据完整性**：更少的冗余意味着更少出现不一致的机会。如果你在一个地方更新了地址，那么所有需要它的地方都会同步更新。
- **防止异常**：规范化有助于防止以下问题：
  1. **插入异常**：由于缺少相关信息，难以添加新数据。
  2. **更新异常**：不得不在多行中更新同一信息。
  3. **删除异常**：在删除看似无关的东西时，意外丢失有价值的信息。
- **更易于理解和维护**：规范化后的数据库通常逻辑结构更清晰，更容易理解、查询和修改。
</Callout>

规范化通常用“范式”（1NF、2NF、3NF 及更高范式）来描述。虽然细节可能相当技术化，但核心思想很直接：

#### 1NF（第一范式）：`原子值`

**目标**：每一列都应保存一个单一的、不可再分的值。单个单元格内不能有重复的数据组

**示例**：与其用一个 `address` 列存储 `123 Main St, City, USA`，你不如
把它拆分成独立的列：`street_address`、`city`、`state`、`zip_code`。

```sql
-- 未规范化（违反 1NF）
CREATE TABLE [Customers_Unnormalized] (
    [customer_id] INT PRIMARY KEY,
    [name] VARCHAR(255),
    [address] VARCHAR(255) -- 问题：一列中有多条信息
);

-- 规范化到 1NF
CREATE TABLE [Customers_1NF] (
    [customer_id] INT PRIMARY KEY,
    [name] VARCHAR(255),
    [street_address] VARCHAR(255),
    [city] VARCHAR(255),
    [state] VARCHAR(255),
    [zip_code] VARCHAR(10)
);
```

#### 2NF（第二范式）：`消除依赖于部分键的冗余数据`

**目标**：当你有一个带复合主键（由两列或更多列组成的主键）的表时适用。
2NF 确保所有非键属性都完全依赖于整个复合主键，而不仅仅是一部分。

假设我们有一个名为 `order_items` 的表。这个表记录订单中的商品，我们使用复合主键（`order_id`、`product_id`），
因为一个订单可以包含多个相同的商品（尽管在这个简化示例中，为清晰起见，我们假设每个商品在每个订单中
只出现一次，但复合键的逻辑仍然适用）。

<Callout collapsed="展开查看可视化示例">
```sql
CREATE TABLE [OrderItems_Unnormalized] (
    [order_id] INT,
    [product_id] VARCHAR(10),
    [product_name] VARCHAR(100),
    [product_price] DECIMAL(10, 2),
    [quantity] INT,
    [order_date] DATE,
    PRIMARY KEY ([order_id], [product_id]) -- 复合主键
);

INSERT INTO [OrderItems_Unnormalized] ([order_id], [product_id], [product_name], [product_price], [quantity], [order_date]) VALUES
(101, 'A123', 'Laptop', 1200.00, 1, '2023-10-27'),
(101, 'B456', 'Mouse', 25.00, 2, '2023-10-27'),
(102, 'A123', 'Laptop', 1200.00, 1, '2023-10-28'),
(103, 'C789', 'Keyboard', 75.00, 1, '2023-10-29');
```
```
+------------------------------------------------------------------------------------+
| OrderItems_Unnormalized                                                            |
+------------------------------------------------------------------------------------+
| PK (order_id, product_id) | product_name | product_price | quantity | order_date   |
+------------------------------------------------------------------------------------+
| 101, A123               | Laptop       | 1200.00       | 1        | 2023-10-27     |
| 101, B456               | Mouse        | 25.00         | 2        | 2023-10-27     |
| 102, A123               | Laptop       | 1200.00       | 1        | 2023-10-28     |
| 103, C789               | Keyboard     | 75.00         | 1        | 2023-10-29     |
+------------------------------------------------------------------------------------+
```
</Callout>

**问题**：注意，只要同一个 `product_id` 出现在不同订单中，`product_name` 和 `product_price` 就会重复。
这些属性只依赖于 `product_id`，而 `product_id` 只是复合主键（`order_id`、`product_id`）的一部分，并非整个键。
这就是部分依赖。

要实现 2NF，我们需要移除这些部分依赖的属性（`product_name`、`product_price`），并把它们放到一个单独的表中，
让它们完全依赖于那个新表的主键。

<Callout collapsed="规范化到 2NF：可视化说明">
```
+-------------------+     1:M     +---------------------------+
| Products          | <---------- | OrderItems_2NF            |
+-------------------+             +---------------------------+
| PK product_id     |             | PK (order_id, product_id) |
| product_name      |             | quantity                  |
| product_price     |             | order_date                |
+-------------------+             | FK product_id             |
                                  +---------------------------+
```
```sql
CREATE TABLE [Products] (
    [product_id] VARCHAR(10) PRIMARY KEY,
    [product_name] VARCHAR(100),
    [product_price] DECIMAL(10, 2)
);

CREATE TABLE [OrderItems_2NF] (
    [order_id] INT,
    [product_id] VARCHAR(10),
    [quantity] INT,
    [order_date] DATE,
    PRIMARY KEY ([order_id], [product_id]), -- 复合主键保持不变
    FOREIGN KEY ([product_id]) REFERENCES [Products]([product_id]) -- 指向 Products 的外键
);

-- 向 Products 插入数据
INSERT INTO [Products] ([product_id], [product_name], [product_price]) VALUES
('A123', 'Laptop', 1200.00),
('B456', 'Mouse', 25.00),
('C789', 'Keyboard', 75.00);

-- 向 OrderItems_2NF 插入数据（引用 Products）
INSERT INTO [OrderItems_2NF] ([order_id], [product_id], [quantity], [order_date]) VALUES
(101, 'A123', 1, '2023-10-27'),
(101, 'B456', 2, '2023-10-27'),
(102, 'A123', 1, '2023-10-28'),
(103, 'C789', 1, '2023-10-29');
```
</Callout>

#### 3NF（第三范式）：`消除依赖于非键属性的冗余数据`

**目标**：移除依赖于其它非键属性的数据。这关乎消除传递依赖。

**问题**：假设我们有一个 `suppliers` 表。我们存储供应商信息，包括他们的 `zip_code`、`city` 和 `state`。`supplier_id` 是主键。

<Callout collapsed="">
```sql
CREATE TABLE [suppliers] (
    [supplier_id] VARCHAR(10) PRIMARY KEY,
    [supplier_name] VARCHAR(255),
    [zip_code] VARCHAR(10),
    [city] VARCHAR(100),
    [state] VARCHAR(50)
);

INSERT INTO [suppliers] ([supplier_id], [supplier_name], [zip_code], [city], [state]) VALUES
('S1', 'Acme Corp', '12345', 'Anytown', 'NY'),
('S2', 'Beta Inc', '67890', 'Otherville', 'CA'),
('S3', 'Gamma Ltd', '12345', 'Anytown', 'NY');
```
```
+---------------------------------------------------------------+
| suppliers                                                     |
+---------------------------------------------------------------+
| PK supplier_id | supplier_name | zip_code | city      | state |
+---------------------------------------------------------------+
| S1             | Acme Corp     | 12345    | Anytown    | NY   |
| S2             | Beta Inc      | 67890    | Otherville | CA   |
| S3             | Gamma Ltd     | 12345    | Anytown    | NY   |
+---------------------------------------------------------------+
```
</Callout>

**解决方案**：要实现 3NF，我们移除依赖于非键属性的属性（`city`、`state` 依赖于 `zip_code`），
并把它们放到一个以该非键属性本身（`zip_code`）为键的单独表中。

<Callout collapsed="规范化到 3NF：可视化说明">
```
+-------------------+     1:M     +--------------------+
| zip_codes         | <---------- | suppliers          |
+-------------------+             +--------------------+
| PK zip_code       |             | PK supplier_id     |
| city              |             | supplier_name      |
| state             |             | FK zip_code        |
+-------------------+             +--------------------+
```
```sql
CREATE TABLE [zip_codes] (
    [zip_code] VARCHAR(10) PRIMARY KEY,
    [city] VARCHAR(100),
    [state] VARCHAR(50)
);

CREATE TABLE [suppliers] (
    [supplier_id] VARCHAR(10) PRIMARY KEY,
    [supplier_name] VARCHAR(255),
    [zip_code] VARCHAR(10), -- 指向 zip_codes 的外键
    FOREIGN KEY ([zip_code]) REFERENCES [zip_codes]([zip_code])
);

-- 向 zip_codes 插入数据
INSERT INTO [zip_codes] ([zip_code], [city], [state]) VALUES
('12345', 'Anytown', 'NY'),
('67890', 'Otherville', 'CA');

-- 向 suppliers 插入数据（引用 zip_codes）
INSERT INTO [suppliers] ([supplier_id], [supplier_name], [zip_code]) VALUES
('S1', 'Acme Corp', '12345'),
('S2', 'Beta Inc', '67890'),
('S3', 'Gamma Ltd', '12345');
```
</Callout>

<Callout title="值得了解">
还有其它范式，例如 `4NF`、`5NF`、`6NF`、`EKNF`、`ETNF` 和 `DKNF`。我们这里不会涉及它们，但我们会
在我们的指南和教程板块中为它们创建一套专门的教程。
</Callout>

### 数据库关系
#### 一对一

在一对一关系中，`table A` 中的每条记录至多与 `table B` 中的一条记录相关，而 `table B` 中的每条记录
至多与 `table A` 中的一条记录相关。这是一种非常直接的、排他的配对关系。

<Callout collapsed="用例与示例">
1. **用户档案与用户账户详情**：想象一个网站。每个用户账户（在 Users 表中）可能恰好对应一个包含更详细信息的用户档案（在 UserProfiles 表中）。
2. **员工与停车位**：一个 Employees 表和一个 ParkingSpaces 表。每个员工至多可能被分配一个停车位，而每个停车位至多分配给一个员工。
3. **为了组织而拆分表**：有时，出于更好的组织或安全原因，你可能会把一个非常宽的表拆分成两个，同时保持它们之间 1-1 的关系。

```
Table A (One Side)      Table B (One Side)
+---------+             +---------+
| PK (A)  | <---------> | FK (A)  | (Foreign Key referencing Table A)
| ...     |             | ...     |
+---------+             +---------+
```
</Callout>


#### 一对多

在一对多关系中，`table A` 中的一条记录可以与 `table B` 中的多条记录相关，但 `table B` 中的每条
记录至多与 `table A` 中的一条记录相关。可以把它看作“父子”关系。

<Callout collapsed="用例与示例">
1. **客户与订单**：一个客户可以下很多订单，但每个订单只属于一个客户。
2. **作者与书籍**：一个作者可以写很多本书，但（这里简化一下来说）每本书由一个主要作者撰写。
3. **部门与员工**：一个部门可以有很多员工，但每个员工只属于一个部门。

```
Table A (One Side)      Table B (Many Side)
+---------+             +---------+
| PK (A)  | ----------> | FK (A)  | (Foreign Key referencing Table A)
| ...     |             | ...     |
+---------+             +---------+
     (One)                  (Many)
```
</Callout>

#### 多对多

在多对多关系中，`table A` 中的一条记录可以与 `table B` 中的多条记录相关，并且 `table B` 中的一条
记录可以与 `table A` 中的多条记录相关。这是一种更复杂的、双向的关系。

<Callout collapsed="用例与示例">
1. **学生与课程**：一个学生可以选修多门课程，而一门课程可以有很多学生选修。
2. **产品与类别**：一个产品可以属于多个类别（例如，一件“T 恤”可以
属于“服装”和“夏装”类别），而一个类别可以包含很多产品。
3. **作者与书籍**：一本书可以由多个作者撰写，而一个作者可以写多本书。

```
Table A (Many Side)    Junction Table      Table B (Many Side)
+---------+          +-------------+     +---------+
| PK (A)  | -------->| FK (A)      | <----| FK (B)  |
| ...     |          | FK (B)      |     | ...     |
+---------+          +-------------+     +---------+
     (Many)             (Junction)          (Many)
```
</Callout>

多对多关系并不是通过两个主表之间的外键直接实现的。
相反，你需要一个 `junction` 表（也称为关联表或桥接表）。
这个表充当中间媒介，将两个表中的记录连接起来。

```sql
-- Students 表（多的一方）
CREATE TABLE [students] (
    [id] INT PRIMARY KEY,
    [name] VARCHAR(255)
);

-- Courses 表（多的一方）
CREATE TABLE [courses] (
    [id] INT PRIMARY KEY,
    [name] VARCHAR(255),
    [credits] INT
);

-- 交叉表：Enrollments（连接 Students 和 Courses - M-M 关系）
CREATE TABLE [enrollments] (
    [id] INT IDENTITY(1,1) PRIMARY KEY, -- 可选，但对交叉表来说是个好做法
    [student_id] INT,
    [course_id] INT,
    [enrollment_date] DATE,
    -- 复合外键（通常是复合主键或唯一约束的一部分）
    FOREIGN KEY ([student_id]) REFERENCES [students]([id]),
    FOREIGN KEY ([course_id]) REFERENCES [courses]([id]),
    UNIQUE ([student_id], [course_id]) -- 防止同一学生和课程出现重复选课
);
```

### 为什么要使用外键？

你可能会把外键约束简单地理解为一种验证数据的方式——确保
当你在外键列中输入一个值时，该值确实存在于另一张表的主键
列中。你的理解部分是对的！这种值检查正是外键所使用的机制。

但关键是要理解，这种验证并不是最终目的，而是通往一个更宏大目标的
手段。外键约束从根本上关乎：

<Callout collapsed="1. 显式地定义并强制实施关系">

我们讨论过客户与订单之间的 `One-to-Many` 这类关系。
外键是 SQL 语言用来告诉数据库的方式：

> 嘿数据库，我想在这里强制实施一个 1-M 关系。Orders 表的 customer_id 列中的
每个值，都必须对应 Customers 表中一个有效的 customer_id。

这不只是一个建议；它是数据库会主动强制实施的约束。
因为外键，数据库变得能够感知关系。
</Callout>

<Callout collapsed="2. 维护参照完整性">
- 这是关系语境下“数据完整性”的核心。参照完整性意味着
表之间的关系随时间保持一致和有效。
- 外键可以防止孤儿记录。什么是孤儿记录？在我们的客户-订单示例中，
一个存在于 Orders 表中、但在 Customers 表中没有对应客户的订单
就是一个孤儿。外键可以防止这种情况发生（或者控制当你尝试删除一个
有订单的客户时会发生什么——通过 CASCADE、SET NULL 等）。
- 为什么防止孤儿很重要？孤儿记录会破坏数据的逻辑结构。
如果你有一个没有客户的订单，你就失去了关键上下文。查询会变得不可靠，报表
会变得不准确，你的应用逻辑也可能崩溃。

**示例**：
```
如果没有外键，你可能会在客户的订单仍然存在于 Orders 表时，意外地从 Customers
表中删除该客户。突然之间，你就有了指向一个不再存在的客户的订单！
外键约束可以防止这种数据不一致。
```
</Callout>

<Callout collapsed="3. 促进数据库设计与理解">
- 外键不只是关乎技术上的强制实施；它们也是数据库设计文档的关键组成部分。
- 当你在数据库 schema 中看到一个外键时，它立即告诉你：
`表 'X' 以这种方式与表 'Y' 相关联。` 它是关系的一个清晰的可视化和结构化指示。
- 这让数据库更容易理解、维护，并能随时间演进。新开发者可以快速
掌握数据库不同部分是如何连接的。
</Callout>

本质上，外键约束不只是关于检查值；它们关乎：

1. 定义数据关系的规则
2. 在数据库层面主动强制实施这些规则
3. 在这些关系中保证数据完整性和一致性
4. 让你的数据库更健壮、更可靠、更易理解

### 为什么不使用外键？

虽然外键非常有益，但在某些场景下，你可能会重新考虑或谨慎使用外键。
这些通常是边缘情况，并且往往涉及权衡。

<Callout collapsed="1. 极高写入环境中的性能开销">
- **场景**：极高吞吐量的事务系统（例如，实时日志记录、非常高频的交易
平台、大规模 IoT 数据摄取）。
- **说明**：每次你向带外键的表中插入或更新数据时，数据库系统
都需要执行检查以确保参照完整性。在极高写入的场景中，这些
检查会引入虽小但可能明显的性能开销。
</Callout>

<Callout collapsed="2. 分布式数据库系统和跨节点外键：">
- **场景**：数据分布在多个数据库节点或集群中的系统（常见于分片数据库、云环境和微服务）。
- **说明**：跨节点外键会引入显著的复杂性和性能开销。验证参照完整性需要在节点之间通信，从而导致延迟增加。为保持一致性所需的分布式事务也更复杂，且性能可能不如本地事务。在此类架构中，可以考虑用应用层的数据完整性检查或最终一致性模型作为替代方案。
</Callout>

<Callout collapsed="3. 遗留系统以及与关系型之外数据的集成：">
- **场景**：将关系型数据库与较旧的遗留系统或非关系型数据存储（例如，NoSQL、平面文件、外部 API）集成。
- **说明**：遗留系统或非关系型数据可能无法始终遵循外键强制实施的参照完整性规则。在这种情况下强加外键可能导致数据导入问题、数据不一致，并且可能需要复杂的数据转换或应用层完整性管理作为替代。你可能需要仔细评估外部来源的数据质量和一致性，并可能依赖应用逻辑或 ETL 流程来保证数据完整性，而不是在数据库层面严格强制外键。
</Callout>

你也可以查看 PlanetScale 团队在他们[文章](https://planetscale.com/docs/learn/operating-without-foreign-key-constraints#why-does-planetscale-not-recommend-constraints)中的一些精彩解释

### 多态关系

多态关系是一个更高级的概念，它允许单个关系指向
不同类型的实体或表。当你拥有共享某些共性的不同类型的数据时，
它关乎创建更灵活、更具适应性的关系。

假设你有一个 `activities` 日志。一个 activity 可以是一个 `comment`、一个 `like` 或一个 `share`。
每种 `activity` 类型都有不同的细节。与其为每种 activity 类型以及它们所关联的事物
创建单独的表和关系，你可以使用多态方法。

<Callout collapsed="常见场景与示例">
- **评论/评价**：一条“Comment”可能与不同类型的内容相关：文章、产品、视频等。
与其在 Comments 表中为 article_id、product_id、video_id 各设一列，你可以使用
多态关系。
```
+---------------------+
| **Comments**        |
+---------------------+
| PK comment_id       |
| commentable_type    | ------>  [Polymorphic Relationship]
| commentable_id      | -------->
| user_id             |
| comment_text        |
| ...                 |
+---------------------+
          ^
          |
+---------------------+    +---------------------+    +---------------------+
| **Articles**        |    | **Products**        |    | **Videos**          |
+---------------------+    +---------------------+    +---------------------+
| PK article_id       |    | PK product_id       |    | PK video_id         |
| ...                 |    | ...                 |    | ...                 |
+---------------------+    +---------------------+    +---------------------+
```
- **通知：** 一条通知可能与用户、订单、系统事件等相关。
```
+----------------------+
| **Notifications**    |
+----------------------+
| PK notification_id  |
| notifiable_type     | ------>  [Polymorphic Relationship]
| notifiable_id       | -------->
| user_id             |
| message             |
| ...                  |
+----------------------+
           ^
           |
+---------------------+    +---------------------+    +-----------------------+
| **Users**           |    | **Orders**          |    | **System Events**     |
+---------------------+    +---------------------+    +-----------------------+
| PK user_id          |    | PK order_id         |    | PK event_id           |
| ...                 |    | ...                 |    | ...                   |
+---------------------+    +---------------------+    +-----------------------+
```
</Callout>

多态关系更加复杂，通常在应用层处理，或者
使用更高级的数据库特性（取决于具体的数据库系统）。标准 SQL
并不像处理常规外键那样，对强制实施多态外键约束提供直接的、内置的支持。
