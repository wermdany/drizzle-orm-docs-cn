# Drizzle Relations 基础

在数据库的世界里，尤其是关系型数据库中，关系的概念绝对是基础中的基础。
把“关系”理解为不同数据片段之间的连接和关联。就像在现实生活中，
人与人之间有各种关系，或者物品与类别存在关联一样，数据库使用关系来建模不同类型的信息
是如何连接并协同工作的。

### 规范化
规范化是组织数据库中数据的过程，目的是减少冗余（重复）并提高数据完整性
（准确性和一致性）。可以把它想象成整理一个凌乱的文件柜。与其把所有
纸张都塞进一个文件夹，不如把它们整理到逻辑清晰的文件夹和分类中，让一切更容易查找和管理。

<Callout collapsed="为什么规范化很重要？">
- **减少数据冗余**：想象一下，每次客户下单时都存储他们的地址。如果地址变了，你就得在多个地方更新它！规范化帮助你在一处存储信息，并从其他位置引用它，从而最大限度地减少重复。
- **提高数据完整性**：冗余越少，出现不一致的机会就越少。如果你在一处更新了地址，所有需要它的地方也都更新了。
- **防止异常**：规范化有助于防止以下问题：
  1. **插入异常**：由于缺少相关信息而难以添加新数据。
  2. **更新异常**：不得不在多行中更新同一条信息。
  3. **删除异常**：在删除看似无关的东西时意外丢失有价值的信息。
- **更容易理解和维护**：规范化的数据库通常结构更具逻辑性，更容易理解、查询和修改。
</Callout>

规范化通常用“范式”（1NF、2NF、3NF 及更高范式）来描述。虽然细节可能相当技术化，但核心思想很直白：

#### 1NF（第一范式）：`Atomic Values`

**目标**：每一列都应保存一个单一的、不可再分的值。单个单元格内不应有重复的数据组

**示例**：与其用单个 `address` 列存储 `123 Main St, City, USA`，你应该
把它拆分成单独的列：`street_address`、`city`、`state`、`zip_code`。

```sql
-- 未规范化（违反 1NF）
CREATE TABLE "Customers_Unnormalized" (
    "customer_id" INTEGER PRIMARY KEY,
    "name" VARCHAR(255),
    "address" VARCHAR(255) -- 问题：一列中存放了多条信息
);

-- 规范化到 1NF
CREATE TABLE "Customers_1NF" (
    "customer_id" INTEGER PRIMARY KEY,
    "name" VARCHAR(255),
    "street_address" VARCHAR(255),
    "city" VARCHAR(255),
    "state" VARCHAR(255),
    "zip_code" VARCHAR(10)
);
```

#### 2NF（第二范式）：`Eliminate Redundant Data Dependent on Part of the Key`

**目标**：当你有一张带有复合主键（由两个或更多列组成的主键）的表时适用。
2NF 确保所有非键属性都完全依赖于整个复合主键，而不仅仅是其中的一部分。

假设我们有一张名为 `order_items` 的表。这张表记录订单中的商品，我们使用复合主键（`order_id`、`product_id`），
因为一个订单可以包含多个相同的商品（不过在这个简化示例中，为了清晰起见，我们假设每个商品在
每个订单中只出现一次，但复合键的逻辑仍然适用）。

<Callout collapsed="展开查看可视化示例">
```sql
CREATE TABLE "OrderItems_Unnormalized" (
    "order_id" INTEGER,
    "product_id" VARCHAR(10),
    "product_name" VARCHAR(100),
    "product_price" DECIMAL(10, 2),
    "quantity" INTEGER,
    "order_date" DATE,
    PRIMARY KEY ("order_id", "product_id") -- 复合主键
);

INSERT INTO "OrderItems_Unnormalized" ("order_id", "product_id", "product_name", "product_price", "quantity", "order_date") VALUES
(101, 'A123', 'Laptop', 1200.00, 1, '2023-10-27'),
(101, 'B456', 'Mouse', 25.00, 2, '2023-10-27'),
(102, 'A123', 'Laptop', 1200.00, 1, '2023-10-28'),
(103, 'C789', 'Keyboard', 75.00, 1, '2023-10-29');
```
```
+------------------------------------------------------------------------------------+
| OrderItems_Unnormalized                                                            |
+------------------------------------------------------------------------------------+
| PK (order_id, product_id) | product_name | product_price | quantity | order_date   |
+------------------------------------------------------------------------------------+
| 101, A123               | Laptop       | 1200.00       | 1        | 2023-10-27     |
| 101, B456               | Mouse        | 25.00         | 2        | 2023-10-27     |
| 102, A123               | Laptop       | 1200.00       | 1        | 2023-10-28     |
| 103, C789               | Keyboard     | 75.00         | 1        | 2023-10-29     |
+------------------------------------------------------------------------------------+
```
</Callout>

**问题**：请注意，只要同一个 `product_id` 出现在不同订单中，`product_name` 和 `product_price` 就会重复。
这些属性只依赖于 `product_id`，而它是复合主键（`order_id`、`product_id`）的一部分，但并非整个键。
这就是部分依赖。

要达到 2NF，我们需要移除这些部分依赖的属性（`product_name`、`product_price`），并把它们放到另一张表中，
使它们完全依赖于那张新表的主键。

<Callout collapsed="规范化到 2NF：可视化说明">
```
+-------------------+     1:M     +---------------------------+
| Products          | <---------- | OrderItems_2NF            |
+-------------------+             +---------------------------+
| PK product_id     |             | PK (order_id, product_id) |
| product_name      |             | quantity                  |
| product_price     |             | order_date                |
+-------------------+             | FK product_id             |
                                  +---------------------------+
```
```sql
CREATE TABLE "Products" (
    "product_id" VARCHAR(10) PRIMARY KEY,
    "product_name" VARCHAR(100),
    "product_price" DECIMAL(10, 2)
);

CREATE TABLE "OrderItems_2NF" (
    "order_id" INTEGER,
    "product_id" VARCHAR(10),
    "quantity" INTEGER,
    "order_date" DATE,
    PRIMARY KEY ("order_id", "product_id"), -- 复合主键保留
    FOREIGN KEY ("product_id") REFERENCES "Products"("product_id") -- 指向 Products 的外键
);

-- 向 Products 插入数据
INSERT INTO "Products" ("product_id", "product_name", "product_price") VALUES
('A123', 'Laptop', 1200.00),
('B456', 'Mouse', 25.00),
('C789', 'Keyboard', 75.00);

-- 向 OrderItems_2NF 插入数据（引用 Products）
INSERT INTO "OrderItems_2NF" ("order_id", "product_id", "quantity", "order_date") VALUES
(101, 'A123', 1, '2023-10-27'),
(101, 'B456', 2, '2023-10-27'),
(102, 'A123', 1, '2023-10-28'),
(103, 'C789', 1, '2023-10-29');
```
</Callout>

#### 3NF（第三范式）：`Eliminate Redundant Data Dependent on Non-Key Attributes`

**目标**：移除以其他非键属性为依赖的数据。这涉及消除传递依赖。

**问题**：假设我们有一张 `suppliers` 表。我们存储供应商信息，包括他们的 `zip_code`、`city` 和 `state`。`supplier_id` 是主键。

<Callout collapsed="">
```sql
CREATE TABLE "suppliers" (
    "supplier_id" VARCHAR(10) PRIMARY KEY,
    "supplier_name" VARCHAR(255),
    "zip_code" VARCHAR(10),
    "city" VARCHAR(100),
    "state" VARCHAR(50)
);

INSERT INTO "suppliers" ("supplier_id", "supplier_name", "zip_code", "city", "state") VALUES
('S1', 'Acme Corp', '12345', 'Anytown', 'NY'),
('S2', 'Beta Inc', '67890', 'Otherville', 'CA'),
('S3', 'Gamma Ltd', '12345', 'Anytown', 'NY');
```
```
+---------------------------------------------------------------+
| suppliers                                                     |
+---------------------------------------------------------------+
| PK supplier_id | supplier_name | zip_code | city      | state |
+---------------------------------------------------------------+
| S1             | Acme Corp     | 12345    | Anytown    | NY   |
| S2             | Beta Inc      | 67890    | Otherville | CA   |
| S3             | Gamma Ltd     | 12345    | Anytown    | NY   |
+---------------------------------------------------------------+
```
</Callout>

**解决方案**：要达到 3NF，我们移除依赖于非键属性的属性（`city`、`state` 依赖于 `zip_code`），并将
它们放入一张以该非键属性本身（`zip_code`）为键的单独表中。

<Callout collapsed="规范化到 3NF：可视化说明">
```
+-------------------+     1:M     +--------------------+
| zip_codes         | <---------- | suppliers          |
+-------------------+             +--------------------+
| PK zip_code       |             | PK supplier_id     |
| city              |             | supplier_name      |
| state             |             | FK zip_code        |
+-------------------+             +--------------------+
```
```sql
CREATE TABLE "zip_codes" (
    "zip_code" VARCHAR(10) PRIMARY KEY,
    "city" VARCHAR(100),
    "state" VARCHAR(50)
);

CREATE TABLE "suppliers" (
    "supplier_id" VARCHAR(10) PRIMARY KEY,
    "supplier_name" VARCHAR(255),
    "zip_code" VARCHAR(10), -- 指向 zip_codes 的外键
    FOREIGN KEY ("zip_code") REFERENCES "zip_codes"("zip_code")
);

-- 向 zip_codes 插入数据
INSERT INTO "zip_codes" ("zip_code", "city", "state") VALUES
('12345', 'Anytown', 'NY'),
('67890', 'Otherville', 'CA');

-- 向 suppliers 插入数据（引用 zip_codes）
INSERT INTO "suppliers" ("supplier_id", "supplier_name", "zip_code") VALUES
('S1', 'Acme Corp', '12345'),
('S2', 'Beta Inc', '67890'),
('S3', 'Gamma Ltd', '12345');
```
</Callout>

<Callout title="值得了解">
还有额外的范式，例如 `4NF`、`5NF`、`6NF`、`EKNF`、`ETNF` 和 `DKNF`。我们不会在这里介绍它们，但我们会在
指南和教程部分为它们专门创建一套教程。
</Callout>

### 数据库关系
#### 一对一

在一对一关系中，`表 A` 中的每条记录最多与 `表 B` 中的一条记录相关联，而 `表 B` 中的每条记录
最多与 `表 A` 中的一条记录相关联。这是一种非常直接、排他的配对关系。

<Callout collapsed="使用场景与示例">
1. **用户档案与用户账户详情**：想象一个网站。每个用户账户（在 Users 表中）可能恰好对应一个用户档案（在 UserProfiles 表中），其中包含更详细的信息。
2. **员工与停车位**：一张 Employees 表和一张 ParkingSpaces 表。每个员工最多可能被分配一个停车位，而每个停车位最多分配给一个员工。
3. **为组织管理而拆分表**：有时，为了更好的组织性或安全性，你可能会把一张非常宽的表拆成两张，并保持它们之间的一对一关系。

```
表 A（一端）             表 B（一端）
+---------+             +---------+
| PK (A)  | <---------> | FK (A)  | （引用表 A 的外键）
| ...     |             | ...     |
+---------+             +---------+
```
</Callout>


#### 一对多

在一对多关系中，`表 A` 中的一条记录可以与 `表 B` 中的多条记录相关联，但 `表 B` 中的每条
记录最多与 `表 A` 中的一条记录相关联。可以把它理解为“父子”关系。

<Callout collapsed="使用场景与示例">
1. **客户与订单**：一个客户可以下很多订单，但每个订单只属于一个客户。
2. **作者与书籍**：一个作者可以写很多书，但（这里简化一下）每本书由一位主要作者撰写。
3. **部门与员工**：一个部门可以有很多员工，但每个员工只属于一个部门。

```
表 A（一端）             表 B（多端）
+---------+             +---------+
| PK (A)  | ----------> | FK (A)  | （引用表 A 的外键）
| ...     |             | ...     |
+---------+             +---------+
     (一端)                (多端)
```
</Callout>

#### 多对多

在多对多关系中，`表 A` 中的一条记录可以与 `表 B` 中的多条记录相关联，并且 `表 B` 中的一条
记录也可以与 `表 A` 中的多条记录相关联。这是一种更复杂的双向关系。

<Callout collapsed="使用场景与示例">
1. **学生与课程**：一个学生可以选修很多课程，一门课程也可以有很多学生选修。
2. **商品与分类**：一个商品可以属于多个分类（例如一件“T 恤”可以同时属于“服装”和“夏季服饰”分类），而一个分类可以包含很多商品。
3. **作者与书籍**：一本书可以由多位作者共同撰写，而一位作者可以写多本书。

```
表 A（多端）            联结表                表 B（多端）
+---------+          +-------------+     +---------+
| PK (A)  | -------->| FK (A)      | <----| FK (B)  |
| ...     |          | FK (B)      |     | ...     |
+---------+          +-------------+     +---------+
     (多端)             (联结表)             (多端)
```
</Callout>

多对多关系不是通过两张主表之间的外键直接实现的。
相反，你需要一张 `junction` 表（也称为关联表或桥接表）。
这张表充当连接两张表中记录的中介。

```sql
-- Students 表（多端）
CREATE TABLE "students" (
    "id" INTEGER PRIMARY KEY,
    "name" VARCHAR(255)
);

-- Courses 表（多端）
CREATE TABLE "courses" (
    "id" INTEGER PRIMARY KEY,
    "name" VARCHAR(255),
    "credits" INTEGER
);

-- 联结表：Enrollments（连接 Students 和 Courses —— 多对多关系）
CREATE TABLE "enrollments" (
    "id" INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- 可选，但这是联结表的好实践
    "student_id" INTEGER,
    "course_id" INTEGER,
    "enrollment_date" DATE,
    -- 复合外键（通常是复合主键或唯一约束的一部分）
    FOREIGN KEY ("student_id") REFERENCES "students"("id"),
    FOREIGN KEY ("course_id") REFERENCES "courses"("id"),
    UNIQUE ("student_id", "course_id") -- 防止同一学生和课程出现重复选课
);
```

### 为什么要用外键？

你可能认为外键约束只是一种验证数据的方式——确保
当你在外键列中输入一个值时，该值确实存在于另一张表的
主键列中。这在部分上是正确的！这种值检查正是外键所使用的机制。

但至关重要的是要理解，这种验证并不是最终目的，它只是实现
一个更大目标的手段。外键约束从根本上关注的是：

<Callout collapsed="1. 明确定义并强制实施关系">

我们已经讨论过诸如客户与订单之间的 `一对多` 这类关系。
外键是 SQL 语言告诉数据库的方式：

> 嘿，数据库，我想在这里强制实施一对多关系。Orders 表的 customer_id 列中的
每个值都必须对应 Customers 表中一个有效的 customer_id。

它不只是一个建议；它是数据库主动强制实施的约束。
因为外键，数据库变得能感知关系。
</Callout>

<Callout collapsed="2. 维护引用完整性">
- 这是关系语境下“数据完整性”的核心。引用完整性意味着
表之间的关系随着时间推移保持一致且有效。
- 外键可以防止出现孤儿记录。什么是孤儿记录？在我们的“客户-订单”示例中，
如果一条订单存在于 Orders 表中，但在 Customers 表中没有对应的客户，
它就是一个孤儿。外键可以防止这种情况发生（或者控制当你尝试
删除一个有订单的客户时会发生什么——通过 CASCADE、SET NULL 等）。
- 为什么防止孤儿很重要？孤儿记录会破坏数据的逻辑结构。
如果你有一条没有客户的订单，你就失去了关键的上下文。查询会变得不可靠，报表
会变得不准确，应用程序的逻辑也可能崩溃。

**示例**：
```
如果没有外键，你可能会在客户的订单仍存在于 Orders 表时，意外地从 Customers
表中删除该客户。突然之间，你就有了一些指向已不存在客户的订单！
外键约束可以防止这种数据不一致。
```
</Callout>

<Callout collapsed="3. 促进数据库设计与理解">
- 外键不只是技术上的强制实施；它们也是数据库设计文档的关键组成部分。
- 当你在数据库 schema 中看到外键时，它会立刻告诉你：
`Table 'X' 以这种方式与 Table 'Y' 相关联。` 它是关系的清晰可视化与结构化指示。
- 这使得数据库随着时间推移更容易理解、维护和演进。新的开发者可以快速
掌握数据库不同部分是如何连接的。
</Callout>

本质上，外键约束不只是检查值；它们关注的是：

1. 定义你的数据关系规则
2. 在数据库层面主动强制实施这些规则
3. 保证这些关系中的数据完整性和一致性
4. 让你的数据库更健壮、更可靠、更易于理解

### 为什么不使用外键？

尽管外键非常有益，但在某些场景下你可能会重新考虑，或谨慎地使用外键。
这些通常是边缘情况，且往往涉及权衡。

<Callout collapsed="1. 极高写入环境下的性能开销">
- **场景**：极高吞吐量的事务系统（例如实时日志记录、超高频交易
平台、大规模 IoT 数据摄取）。
- **说明**：每当你在带外键的表中插入或更新数据时，数据库系统
都需要执行检查以确保引用完整性。在极高写入的场景下，这些
检查会带来虽小但可能可察觉的性能开销。
</Callout>

<Callout collapsed="2. 分布式数据库系统与跨节点外键：">
- **场景**：数据分布在多个数据库节点或集群上的系统（在分片数据库、云环境和微服务中很常见）。
- **说明**：跨节点外键会带来显著的复杂性和性能开销。验证引用完整性需要节点之间通信，从而导致延迟增加。为保持一致性所需的分布式事务也更复杂，性能可能不如本地事务。在此类架构中，可以考虑用应用层的数据完整性检查或最终一致性模型作为替代方案。
</Callout>

<Callout collapsed="3. 遗留系统与非关系型数据的集成：">
- **场景**：将关系型数据库与较老的遗留系统或非关系型数据存储（例如 NoSQL、平面文件、外部 API）集成。
- **说明**：遗留系统或非关系型数据可能无法始终遵守外键强制实施的引用完整性规则。在此类场景中强制使用外键可能导致数据导入问题、数据不一致，反而可能需要复杂的数据转换或应用层的完整性管理。你可能需要仔细评估外部数据源的数据质量和一致性，并可能依赖应用逻辑或 ETL 流程来确保数据完整性，而不是在数据库层面严格强制使用外键。
</Callout>

你也可以查看 PlanetScale 团队在他们[这篇文章](https://planetscale.com/docs/learn/operating-without-foreign-key-constraints#why-does-planetscale-not-recommend-constraints)中的一些精彩解释

### 多态关系

多态关系是一个更高级的概念，它允许单个关系指向
不同类型的实体或表。当你拥有不同类型但又共享某些共性的数据时，
它可以帮助你建立更灵活、适应性更强的关系。

假设你有一个 `activities` 日志。一个活动可能是一个 `comment`、一个 `like` 或一个 `share`。
每种 `activity` 类型都有不同的细节。与其为每种活动类型以及它们所关联的对象
分别创建表和关系，你可能会采用多态的方式。

<Callout collapsed="常见场景与示例">
- **评论/评价**：一条“评论”可能与不同类型的内容相关：文章、商品、视频等。
与其在 Comments 表中分别设置 article_id、product_id、video_id 列，你可以使用
多态关系。
```
+---------------------+
| **Comments**        |
+---------------------+
| PK comment_id       |
| commentable_type    | ------>  [多态关系]
| commentable_id      | -------->
| user_id             |
| comment_text        |
| ...                 |
+---------------------+
          ^
          |
+---------------------+    +---------------------+    +---------------------+
| **Articles**        |    | **Products**        |    | **Videos**          |
+---------------------+    +---------------------+    +---------------------+
| PK article_id       |    | PK product_id       |    | PK video_id         |
| ...                 |    | ...                 |    | ...                 |
+---------------------+    +---------------------+    +---------------------+
```
- **通知：** 一条通知可能与用户、订单、系统事件等相关。
```
+----------------------+
| **Notifications**    |
+----------------------+
| PK notification_id  |
| notifiable_type     | ------>  [多态关系]
| notifiable_id       | -------->
| user_id             |
| message             |
| ...                  |
+----------------------+
           ^
           |
+---------------------+    +---------------------+    +-----------------------+
| **Users**           |    | **Orders**          |    | **System Events**     |
+---------------------+    +---------------------+    +-----------------------+
| PK user_id          |    | PK order_id         |    | PK event_id           |
| ...                 |    | ...                 |    | ...                   |
+---------------------+    +---------------------+    +-----------------------+
```
</Callout>

多态关系更复杂，通常在应用层处理，或者
使用更高级的数据库特性（取决于具体的数据库系统）。标准 SQL
并不像常规外键那样，直接内置支持强制实施多态外键约束。
