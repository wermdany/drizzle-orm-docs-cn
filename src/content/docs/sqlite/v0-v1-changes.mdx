# v1 中的变更

本页展示了从 `drizzle-orm@0.x`、`drizzle-kit@0.x`、`drizzle-seed@0.x` 到最新的 `drizzle-orm@1.0`、`drizzle-kit@1.0`、`drizzle-seed@1.0` 的所有变化

<Callout type="info">
在[这里](/docs/sqlite/upgrade-v1)阅读有关如何升级的更多内容
</Callout>

## 破坏性变更

#### v1.0 之前的外键处理
旧的 `drizzle-kit` 不会把 TS schema 中的外键名称传递到生成的 SQL 中：
```ts {6}
export const table = sqliteTable("table", {
  column1: integer(),
  column2: integer(),
}, (t) => [
  foreignKey({
    name: "name",
    columns: [t.column1],
    foreignColumns: [t.column2],
  }),
]);
```
```sql {5}
-- 之前：生成的 SQL 中没有名称
CREATE TABLE `table` (
	`column1` integer,
	`column2` integer,
	FOREIGN KEY (`column1`) REFERENCES `table`(`column2`) ON UPDATE no action ON DELETE no action
);
```

在执行 `introspect` 时，drizzle-kit 会解析 DDL 来查找约束名称；如果找不到，则使用默认名称。

升级到 v1 后，第一次 `push` 会产生一个重建该表的 diff（数据库中没有名称，而 TS 中有）。**为避免这种情况，请从 TS schema 中移除该外键名称** - 这样就不会生成 diff。

`drizzle-kit generate` 行为符合预期；无需改动。

#### 移除关系查询 v1

RQBv1 已被移除。请改用 [Relational Queries v2](/docs/sqlite/relations) 及其新的 `defineRelations()` API 和新特性。你可以在[这里](/docs/sqlite/relations-v1-v2)找到有关从 rqb v1 迁移到 v2 的更多细节

一套围绕 `defineRelations()` 构建的新关系系统：

```ts
import { defineRelations } from 'drizzle-orm';

const relations = defineRelations(schema, (r) => ({
  users: {
    posts: r.many.posts(),
    profile: r.one.profiles(),
  },
  posts: {
    author: r.one.users({
      from: posts.authorId,
      to: users.id,
    }),
  },
}));
```

#### 新的 Casing API

旧版的 `drizzle({ casing: 'camelCase' })` 已被表/视图/schema 级别的 API 取代：

```ts
import { snakeCase, camelCase } from 'drizzle-orm/pg-core';

export const users = snakeCase.table('users', {
  id: serial().primaryKey(),
  fullName: text(),        // → 数据库中的 full_name
  createdAt: timestamp(),  // → 数据库中的 created_at
});

// 可用于所有实体类型：
snakeCase.table / snakeCase.view / snakeCase.materializedView / snakeCase.schema
camelCase.table / camelCase.view / camelCase.materializedView / camelCase.schema
```

#### 校验器包合并到 `drizzle-orm`

<Callout type="warning">
你仍然可以使用 drizzle-zod/valibot/typebox/arktype 校验包，但所有新的更新都会直接添加到 Drizzle ORM 中
</Callout>

- drizzle-zod -> drizzle-orm/zod
- drizzle-valibot -> drizzle-orm/valibot
- drizzle-typebox -> drizzle-orm/typebox-legacy（使用 @sinclair/typebox）
- drizzle-typebox -> drizzle-orm/typebox（使用 typebox）
- drizzle-arktype -> drizzle-orm/arktype
- 新增 `drizzle-orm/effect-schema` 包

#### `.generatedAlwaysAs()` 仅接受 SQL

```ts
// ❌ 之前 — 接受原始值
.generatedAlwaysAs('some expression')

// ✅ 之后 — 仅接受 sql`` 或 () => sql``
.generatedAlwaysAs(sql`some expression`)
.generatedAlwaysAs(() => sql`some expression`)
```

#### 弃用 `getTableColumns`

请改用 `getColumns`

```ts
// ❌ 之前
import { getTableColumns } from 'drizzle-orm';

const columns = getTableColumns(users);

// ✅ 之后
import { getColumns } from 'drizzle-orm';

const columns = getColumns(users);
```

#### 新的迁移文件夹结构（v3）

**Linked discussion**: [#2832](https://github.com/drizzle-team/drizzle-orm/discussions/2832)

<br/>

- 不再需要 `journal.json`
- 将 SQL 文件和快照分组到独立的迁移文件夹中
- 移除了 `drizzle-kit drop` 命令

这些改动消除了可能与 journal 文件产生的 Git 冲突，并简化了删除或修复冲突迁移的过程

<Callout type="info">
在[这里](/docs/sqlite/upgrade-v1)阅读有关如何升级的更多内容
</Callout>

#### 弃用 `drizzle-kit push --strict`

`--strict` 标志已被移除 — 其行为现在是默认行为。除非传入 `--force` 标志，否则 `drizzle-kit push` 总是会针对可能造成数据丢失的语句提示确认。使用 [drizzle-kit push --explain](/docs/sqlite/drizzle-kit-push) 可以在执行前预览将要运行的 SQL。

#### Drizzle seed：UUID 生成器升级到 v4

UUID 生成器现在会生成符合 RFC 4122 v4 的 UUID，确保与 Zod v4 校验兼容。使用 `{ version: '1' }` 可保留旧行为，或使用 `{ version: '2' | '3' }` 启用更新的生成器。

## 其他特性

#### JIT 映射器（可选启用）

即时（just-in-time）编译的行映射器，使映射速度与使用原始驱动一样快。
你可以在[这里](/docs/sqlite/jit-mappers)了解更多

```ts {1}
const db = drizzle({ ..., jit: true });
```

新增了对 MSSQL 方言的支持。你可以在[这里](/docs/mssql/get-started-mssql)阅读更多

#### 新的 CockroachDB 方言

新增了对 CockroachDB 方言的支持。你可以在[这里](/docs/cockroach/get-started-cockroach)阅读更多

#### 通过 `.as()` 设置列别名

你可以在[这里](/docs/sqlite/aliases)了解更多别名相关的信息
```ts
const query = db
  .select({ age: users.age.as('ageOfUser'), id: users.id.as('userId') })
  .from(users)
  .orderBy(asc(users.id.as('userId')));
```

#### `drizzle-kit pull --init`

创建 drizzle 迁移表，并将第一个拉取的迁移标记为已应用。你可以在[这里](/docs/sqlite/drizzle-kit-pull)阅读更多

#### `drizzle-kit push --explain`

展示将要执行的 SQL，但实际并不运行它。你可以在[这里](/docs/sqlite/drizzle-kit-push)阅读更多

#### `drizzle-kit check` — 交换性检查

检测跨分支的非可交换迁移 — 例如两个分支修改了同一列，或一个分支重命名了另一个分支正在修改的表。

其工作原理：
- 根据快照的 `prevIds` 构建 DAG，以理解分支结构
- 找出分支发生分叉的岔点
- 计算从父快照到每个分支叶子节点的 DDL diff
- 使用一张记录哪些 DDL 语句类型可能相互干扰的覆盖图（footprint map）来检查冲突

如果发现冲突，报告会准确告诉你哪些分支上的哪些迁移不兼容，以及哪些语句相互冲突。

#### `drizzle-kit --ignore-conflicts` 标志

当你确知这些冲突是预期之内时，可绕过可交换性检查。

#### `drizzle-kit generate`：迁移冲突检测

`drizzle-kit generate` 现在会识别跨迁移分支的[不兼容变更](/docs/sqlite/v0-v1-changes#drizzle-kit-check--交换性检查)。使用 `--ignore-conflicts` 可绕过。

#### 迁移表的更新

当你运行 `drizzle-kit up` 时，迁移表会自动升级。会新增两个列：

- **`name`** — 完整的迁移文件夹名称（例如 `20250220153045_brave_wolverine`）
- **`applied_at`** — 迁移执行时的时间戳（已存在的行会用 `NULL` 回填）

| Column | Type | v0 | v1 |
| --- | --- | --- |:---:|
| `id` | integer | 是 | 是 |
| `hash` | text | 是 | 是 |
| `created_at` | numeric | 是 | 是（旧版） |
| `name` | text | — | 新增 |
| `applied_at` | text | — | 新增 |

迁移现在按其完整文件夹名称进行匹配，而不再按时间戳匹配。即使两个迁移在同一秒内生成，名称后缀也能保证唯一性。

升级过程中，现有行会按多步骤策略进行回填：
1. **毫秒匹配** — 将存储的毫秒截断到秒，与本地文件夹时间戳匹配
2. **哈希决胜** — 如果多个迁移共用同一秒，则通过 SQL 哈希区分
3. **仅哈希回退** — 如果毫秒匹配完全失败，则仅按哈希匹配

<br/>
这意味着该升级能处理所有边界情况：普通的单人开发项目、迁移时间极为接近的团队，甚至旧 journal 数据与新文件夹名称无法完全对齐的情况。

#### Migrator 应用所有缺失的迁移

此前，迁移器只会查找创建日期晚于最后一个已应用迁移的本地迁移。现在它会检测并应用**每一个缺失的迁移**，无论时间戳的顺序如何。所有迁移都会按完整文件夹名称（14 位 UTC 时间戳 + 名称后缀）进行匹配。

#### drizzle 配置文件中的顶层 `await`

现在，Node.js 上的 `drizzle.config.ts` 和 schema 文件中支持顶层 `await`。

#### Drizzle-kit：构建系统改进

- 从 `esbuild-register` 迁移到 `tsx` 加载器 — 无缝支持 ESM 和 CJS
- 原生支持 Bun 和 Deno 启动

#### TS Schema 文件处理

只会处理具有以下扩展名的文件：`.js`、`.mjs`、`.cjs`、`.jsx`、`.ts`、`.mts`、`.cts`、`.tsx`。所有其它文件类型都会被忽略。

#### Drizzle Seed：在细化中忽略列

在填充种子数据时跳过特定列 — 将改为使用数据库默认值：

```ts
await seed(db, schema).refine((f) => ({
  users: {
    count: 5,
    columns: {
      name: f.fullName(),
      photo: false, // 跳过 — 将使用数据库默认值
    },
  },
}));
```

#### `min` / `max` 参数

基于时间的生成器现在接受边界值：

```ts
funcs.time({ min: '13:12:13', max: '15:12:13' })
funcs.timestamp({ min: '2024-01-01T00:00:00Z', max: '2025-01-01T00:00:00Z' })
funcs.datetime({ min: '2024-01-01', max: '2025-01-01' })
```
