# Drizzle 关系基础

在数据库的世界中，尤其是关系数据库，关系（relations）的概念绝对是基础性的。
将「关系」理解为不同数据片段之间的连接和链接。就像现实生活中，
人与人之间有关系，或对象与类别相关，数据库使用关系来建模
不同类型的信息如何连接并协同工作。

### 范式化
规范化（Normalization）是组织数据库中数据的过程，以减少冗余（重复）并提高数据完整性
（准确性和一致性）。把它想象成整理一个凌乱的文件柜。与其把所有纸张
塞进一个文件夹，不如将它们整理到逻辑清晰的文件夹和类别中，让一切更容易查找和管理。

<Callout collapsed="为什么规范化很重要？">
- **减少数据冗余**：想象一下每次客户下订单时都存储客户的地址。如果地址发生变化，你必须在多个地方更新它！规范化帮助你将信息存储在一个地方并从其他地方引用它，从而最大限度地减少重复。
- **提高数据完整性**：更少的冗余意味着更少的不一致机会。如果你在一处更新地址，它会在所有需要的地方更新。
- **防止异常**：规范化有助于防止以下问题：
  1. **插入异常**：由于缺少相关信息而难以添加新数据。
  2. **更新异常**：必须在多行中更新相同的信息。
  3. **删除异常**：在删除看似不相关的内容时意外丢失有价值的信息。
- **更易理解和维护**：规范化的数据库通常结构更合理，更容易理解、查询和修改。
</Callout>

规范化通常用「范式」（1NF、2NF、3NF 等）来描述。虽然细节可能相当技术性，但核心思想很直接：

#### 1NF（第一范式）：`原子值`

**目标**：每列应保存单个、不可分割的值。单个单元格内没有重复的数据组

**示例**：与其有一个存储 `123 Main St, City, USA` 的 `address` 列，不如
将其分解为独立的列：`street_address`、`city`、`state`、`zip_code`。

```sql
-- 未规范化（违反 1NF）
CREATE TABLE Customers_Unnormalized (
    customer_id INTEGER PRIMARY KEY,
    name TEXT,
    address TEXT -- 问题：一个列中有多条信息
);

-- 规范化为 1NF
CREATE TABLE Customers_1NF (
    customer_id INTEGER PRIMARY KEY,
    name TEXT,
    street_address TEXT,
    city TEXT,
    state TEXT,
    zip_code TEXT
);
```

#### 2NF（第二范式）：`消除依赖于部分键的冗余数据`

**目标**：适用于具有复合主键（由两个或多个列组成的主键）的表。
2NF 确保所有非键属性完全依赖于整个复合主键，而不仅仅是其中的一部分。

假设我们有一个名为 `order_items` 的表。该表跟踪订单中的商品，我们使用复合主键（`order_id`、`product_id`），
因为一个订单可以包含多个相同的产品（尽管在这个简化示例中，为清晰起见，我们假设每个产品
在每个订单中只出现一次，但复合键逻辑仍然适用）。

<Callout collapsed="展开查看可视化示例">
```sql
CREATE TABLE OrderItems_Unnormalized (
    order_id INTEGER,
    product_id TEXT,
    product_name TEXT,
    product_price REAL,
    quantity INTEGER,
    order_date TEXT,
    PRIMARY KEY (order_id, product_id) -- 复合主键
);

INSERT INTO OrderItems_Unnormalized (order_id, product_id, product_name, product_price, quantity, order_date) VALUES
(101, 'A123', 'Laptop', 1200.00, 1, '2023-10-27'),
(101, 'B456', 'Mouse', 25.00, 2, '2023-10-27'),
(102, 'A123', 'Laptop', 1200.00, 1, '2023-10-28'),
(103, 'C789', 'Keyboard', 75.00, 1, '2023-10-29');
```
```
+------------------------------------------------------------------------------------+
| OrderItems_Unnormalized                                                            |
+------------------------------------------------------------------------------------+
| PK (order_id, product_id) | product_name | product_price | quantity | order_date   |
+------------------------------------------------------------------------------------+
| 101, A123               | Laptop       | 1200.00       | 1        | 2023-10-27     |
| 101, B456               | Mouse        | 25.00         | 2        | 2023-10-27     |
| 102, A123               | Laptop       | 1200.00       | 1        | 2023-10-28     |
| 103, C789               | Keyboard     | 75.00         | 1        | 2023-10-29     |
+------------------------------------------------------------------------------------+
```
</Callout>

**问题**：注意每当相同的 `product_id` 出现在不同订单中时，`product_name` 和 `product_price` 都会重复。
这些属性仅依赖于 `product_id`，它是复合主键（`order_id`、`product_id`）的一部分，而不是整个键。
这是部分依赖。

要实现 2NF，我们需要移除部分依赖的属性（`product_name`、`product_price`），并将它们放在一个单独的表中，在那里它们
完全依赖于该新表的主键。

<Callout collapsed="规范化为 2NF：可视化解释">
```
+-------------------+     1:M     +---------------------------+
| Products          | <---------- | OrderItems_2NF            |
+-------------------+             +---------------------------+
| PK product_id     |             | PK (order_id, product_id) |
| product_name      |             | quantity                  |
| product_price     |             | order_date                |
+-------------------+             | FK product_id             |
                                  +---------------------------+
```
```sql
CREATE TABLE Products (
    product_id TEXT PRIMARY KEY,
    product_name TEXT,
    product_price REAL
);

CREATE TABLE OrderItems_2NF (
    order_id INTEGER,
    product_id TEXT,
    quantity INTEGER,
    order_date TEXT,
    PRIMARY KEY (order_id, product_id), -- 复合主键保持不变
    FOREIGN KEY (product_id) REFERENCES Products(product_id) -- 指向 Products 的外键
);

-- 向 Products 插入数据
INSERT INTO Products (product_id, product_name, product_price) VALUES
('A123', 'Laptop', 1200.00),
('B456', 'Mouse', 25.00),
('C789', 'Keyboard', 75.00);

-- 向 OrderItems_2NF 插入数据（引用 Products）
INSERT INTO OrderItems_2NF (order_id, product_id, quantity, order_date) VALUES
(101, 'A123', 1, '2023-10-27'),
(101, 'B456', 2, '2023-10-27'),
(102, 'A123', 1, '2023-10-28'),
(103, 'C789', 1, '2023-10-29');
```
</Callout>

#### 3NF（第三范式）：`消除依赖于非键属性的冗余数据`

**目标**：移除依赖于其他非键属性的数据。这是关于消除传递依赖。

**问题**：假设我们有一个 `suppliers` 表。我们存储供应商信息，包括其 `zip_code`、`city` 和 `state`。`supplier_id` 是主键。

<Callout collapsed="">
```sql
CREATE TABLE suppliers (
    supplier_id TEXT PRIMARY KEY,
    supplier_name TEXT,
    zip_code TEXT,
    city TEXT,
    state TEXT
);

INSERT INTO suppliers (supplier_id, supplier_name, zip_code, city, state) VALUES
('S1', 'Acme Corp', '12345', 'Anytown', 'NY'),
('S2', 'Beta Inc', '67890', 'Otherville', 'CA'),
('S3', 'Gamma Ltd', '12345', 'Anytown', 'NY');
```
```
+---------------------------------------------------------------+
| suppliers                                                     |
+---------------------------------------------------------------+
| PK supplier_id | supplier_name | zip_code | city      | state |
+---------------------------------------------------------------+
| S1             | Acme Corp     | 12345    | Anytown    | NY   |
| S2             | Beta Inc      | 67890    | Otherville | CA   |
| S3             | Gamma Ltd     | 12345    | Anytown    | NY   |
+---------------------------------------------------------------+
```
</Callout>

**解决方案**：要实现 3NF，我们移除依赖于非键属性的属性（`city`、`state` 依赖于 `zip_code`），并将
它们放入一个由非键属性本身（`zip_code`）作为键的单独表中。

<Callout collapsed="规范化为 3NF：可视化解释">
```
+-------------------+     1:M     +--------------------+
| zip_codes         | <---------- | suppliers          |
+-------------------+             +--------------------+
| PK zip_code       |             | PK supplier_id     |
| city              |             | supplier_name      |
| state             |             | FK zip_code        |
+-------------------+             +--------------------+
```
```sql
CREATE TABLE zip_codes (
    zip_code TEXT PRIMARY KEY,
    city TEXT,
    state TEXT
);

CREATE TABLE suppliers (
    supplier_id TEXT PRIMARY KEY,
    supplier_name TEXT,
    zip_code TEXT, -- 指向 zip_codes 的外键
    FOREIGN KEY (zip_code) REFERENCES zip_codes(zip_code)
);

-- 向 zip_codes 插入数据
INSERT INTO zip_codes (zip_code, city, state) VALUES
('12345', 'Anytown', 'NY'),
('67890', 'Otherville', 'CA');

-- 向 suppliers 插入数据（引用 zip_codes）
INSERT INTO suppliers (supplier_id, supplier_name, zip_code) VALUES
('S1', 'Acme Corp', '12345'),
('S2', 'Beta Inc', '67890'),
('S3', 'Gamma Ltd', '12345');
```
</Callout>

<Callout title="值得了解">
还有其他范式，例如 `4NF`、`5NF`、`6NF`、`EKNF`、`ETNF` 和 `DKNF`。我们在这里不涵盖它们，但我们将在
指南和教程部分为它们创建一套专门教程。
</Callout>

### 数据库关系
#### 一对一

在一对一关系中，`table A` 中的每条记录最多与 `table B` 中的一条记录相关，`table B` 中的每条记录
最多与 `table A` 中的一条记录相关。这是一种非常直接、排他的配对。

<Callout collapsed="使用场景与示例">
1. **用户资料与用户账户详情**：想象一个网站。每个用户账户（在 Users 表中）可能有恰好一个包含更详细信息的用户资料（在 UserProfiles 表中）。
2. **员工与停车位**：一个 Employees 表和一个 ParkingSpaces 表。每个员工最多可能被分配一个停车位，每个停车位最多分配给一个员工。
3. **为组织方便而拆分表**：有时，出于更好的组织或安全原因，你可能会将一个非常宽的表拆分为两个，并在它们之间保持 1-1 关系。

```
Table A (One Side)      Table B (One Side)
+---------+             +---------+
| PK (A)  | <---------> | FK (A)  | (Foreign Key referencing Table A)
| ...     |             | ...     |
+---------+             +---------+
```
</Callout>


#### 一对多

在一对多关系中，`table A` 中的一条记录可以关联到 `table B` 中的多条记录，但
`table B` 中的每条记录最多关联到 `table A` 中的一条记录。可以将其视为「父-子」关系。

<Callout collapsed="使用场景与示例">
1. **客户与订单**：一个客户可以下多个订单，但每个订单只属于一个客户。
2. **作者与书籍**：一个作者可以写多本书，但（为简化起见，我们说）每本书由一个主要作者撰写。
3. **部门与员工**：一个部门可以有很多员工，但每个员工只属于一个部门。

```
Table A (One Side)      Table B (Many Side)
+---------+             +---------+
| PK (A)  | ----------> | FK (A)  | (Foreign Key referencing Table A)
| ...     |             | ...     |
+---------+             +---------+
     (One)                  (Many)
```
</Callout>

#### 多对多

在多对多关系中，`table A` 中的一条记录可以关联到 `table B` 中的多条记录，
`table B` 中的一条记录也可以关联到 `table A` 中的多条记录。这是一种更复杂的双向关系。

<Callout collapsed="使用场景与示例">
1. **学生与课程**：一个学生可以选修多门课程，一门课程可以有很多学生选修。
2. **产品与类别**：一个产品可以属于多个类别（例如，「T-shirt」可以
属于「Clothing」和「Summer Wear」类别），一个类别可以包含多个产品。
3. **作者与书籍**：一本书可以由多位作者撰写，一位作者可以写多本书。

```
Table A (Many Side)    Junction Table      Table B (Many Side)
+---------+          +-------------+     +---------+
| PK (A)  | -------->| FK (A)      | <----| FK (B)  |
| ...     |          | FK (B)      |     | ...     |
+---------+          +-------------+     +---------+
     (Many)             (Junction)          (Many)
```
</Callout>

多对多关系不是通过两个主表之间的外键直接实现的。
相反，你需要一个 `junction` 表（也称为关联表或桥接表）。
该表充当中间人，链接来自两个表的记录。

```sql
-- Students 表（多侧）
CREATE TABLE students (
    id INTEGER PRIMARY KEY,
    name TEXT
);

-- Courses 表（多侧）
CREATE TABLE courses (
    id INTEGER PRIMARY KEY,
    name TEXT,
    credits INTEGER
);

-- 连接表：Enrollments（连接 Students 和 Courses - M-M 关系）
CREATE TABLE enrollments (
    id INTEGER PRIMARY KEY AUTOINCREMENT, -- 可选，但是连接表的良好实践
    student_id INTEGER,
    course_id INTEGER,
    enrollment_date TEXT,
    -- 复合外键（通常是复合主键或唯一约束的一部分）
    FOREIGN KEY (student_id) REFERENCES students(id),
    FOREIGN KEY (course_id) REFERENCES courses(id),
    UNIQUE (student_id, course_id) -- 防止同一学生和课程的重复选课
);
```

### 为什么要用外键？

你可能会认为外键约束只是一种验证数据的方式 —— 确保
当你在外键列中输入值时，该值确实存在于另一个表的
主键列中。你说得部分正确！这种值检查是外键使用的机制。

但至关重要的是要理解，这种验证不是最终目标，而是实现
更大目的的手段。外键约束根本上关乎：

<Callout collapsed="1. 显式定义并强制执行关系">

我们已经讨论过 Customers 和 Orders 之间的 `One-to-Many` 等关系。
外键是 SQL 语言告诉数据库的方式：

> 嘿，数据库，我想在这里强制执行一个 1-M 关系。Orders 表的
customer_id 列中的每个值都必须对应 Customers 表中的一个有效 customer_id。

这不仅仅是一个建议；这是数据库主动强制执行的约束。
由于外键，数据库变得具有关系感知能力。
</Callout>

<Callout collapsed="2. 维护引用完整性">
- 这是关系语境下「数据完整性」的核心。引用完整性意味着
表之间的关系始终保持一致和有效。
- 外键防止孤儿记录。什么是孤儿记录？在我们的 Customer-Order 示例中，
存在于 Orders 表中但 Customers 表中没有对应用户的订单
就是孤儿。外键防止这种情况发生（或控制当你尝试
删除有订单的客户时会发生什么 —— 通过 CASCADE、SET NULL 等）。
- 为什么防止孤儿很重要？孤儿记录会破坏数据的逻辑结构。
如果你有一个没有客户的订单，你就丢失了关键上下文。查询变得不可靠，报告
变得不准确，你的应用逻辑可能崩溃。

**示例**：
```
Without a foreign key, you could accidentally delete a customer from the Customers 
table while their orders still exist in the Orders table. Suddenly, you have orders that point to 
a customer that no longer exists! A foreign key constraint prevents this data inconsistency.
```
</Callout>

<Callout collapsed="3. 促进数据库设计与理解">
- 外键不仅关乎技术强制执行；它们也是数据库设计文档的关键部分。
- 当你在数据库 schema 中看到外键时，它会立即告诉你：
`Table 'X' is related to Table 'Y' in this way.` 它是关系的清晰可视化与结构化指示器。
- 这使数据库更容易理解、维护和随时间演进。新开发者可以快速
掌握数据库不同部分是如何连接的。
</Callout>

本质上，外键约束不仅仅是检查值；它们关乎：

1. 定义数据关系的规则
2. 在数据库层面主动强制执行这些规则
3. 保证这些关系内的数据完整性和一致性
4. 让你的数据库更健壮、可靠和易于理解

### 为什么不用外键？

虽然非常有益，但在某些场景下你可能需要重新考虑或谨慎使用外键。
这些通常是边缘情况，并且往往涉及权衡。

<Callout collapsed="1. 极高写入环境中的性能开销">
- **场景**：极高吞吐量的事务系统（例如实时日志、极高频交易
平台、大规模 IoT 数据摄取）。
- **解释**：每次在有外键的表中插入或更新数据时，数据库系统
都需要执行检查以确保引用完整性。在极高写入的场景中，这些
检查可能引入微小但可能被察觉的性能开销。
</Callout>

<Callout collapsed="2. 分布式数据库系统与跨节点外键：">
- **场景**：数据分布在多个数据库节点或集群中的系统（在分片数据库、云环境和微服务中很常见）。
- **解释**：跨节点外键可能引入显著的复杂性和性能开销。验证引用完整性需要节点间通信，导致延迟增加。维护一致性所需的分布式事务也更复杂，性能可能不如本地事务。在此类架构中，可以考虑使用应用层数据完整性检查或最终一致性模型作为替代方案。
</Callout>

<Callout collapsed="3. 遗留系统与与非关系数据的集成：">
- **场景**：将关系数据库与较旧的遗留系统或非关系数据存储（例如 NoSQL、平面文件、外部 API）集成。
- **解释**：遗留系统或非关系数据可能无法始终遵守外键强制执行的引用完整性规则。在这种情况下强加外键可能导致数据导入问题、数据不一致，并可能需要复杂的数据转换或应用层完整性管理作为替代。你可能需要仔细评估外部源的数据质量和一致性，并可能依赖应用逻辑或 ETL 流程来确保数据完整性，而不是在数据库层面严格要求外键。
</Callout>

你也可以查看 PlanetScale 团队在其 [文章](https://planetscale.com/docs/learn/operating-without-foreign-key-constraints#why-does-planetscale-not-recommend-constraints) 中的一些精彩解释

### 多态关系

多态关系是一个更高级的概念，它允许单个关系指向
不同类型的实体或表。当你拥有共享某些共性的不同类型数据时，
它关乎创建更灵活、适应性更强的关联。

想象你有一个 `activities` 日志。一个活动可能是一个 `comment`、一个 `like` 或一个 `share`。
每种 `activity` 类型都有不同的细节。与其为每种活动类型及它们关联的事物
创建单独的表和关系，你可以使用多态方法。

<Callout collapsed="常见场景与示例">
- **Comments/Reviews**：一个「Comment」可能关联到不同类型的内容：文章、产品、视频等。
与其在 Comments 表中分别设置 article_id、product_id、video_id 列，你可以使用
多态关系。
```
+---------------------+
| **Comments**        |
+---------------------+
| PK comment_id       |
| commentable_type    | ------>  [Polymorphic Relationship]
| commentable_id      | -------->
| user_id             |
| comment_text        |
| ...                 |
+---------------------+
          ^
          |
+---------------------+    +---------------------+    +---------------------+
| **Articles**        |    | **Products**        |    | **Videos**          |
+---------------------+    +---------------------+    +---------------------+
| PK article_id       |    | PK product_id       |    | PK video_id         |
| ...                 |    | ...                 |    | ...                 |
+---------------------+    +---------------------+    +---------------------+
```
- **Notifications：** 一个通知可能关联到用户、订单、系统事件等。
```
+----------------------+
| **Notifications**    |
+----------------------+
| PK notification_id  |
| notifiable_type     | ------>  [Polymorphic Relationship]
| notifiable_id       | -------->
| user_id             |
| message             |
| ...                  |
+----------------------+
           ^
           |
+---------------------+    +---------------------+    +-----------------------+
| **Users**           |    | **Orders**          |    | **System Events**     |
+---------------------+    +---------------------+    +-----------------------+
| PK user_id          |    | PK order_id         |    | PK event_id           |
| ...                 |    | ...                 |    | ...                   |
+---------------------+    +---------------------+    +-----------------------+
```
</Callout>

多态关系更复杂，通常在应用层处理或
使用更高级的数据库功能（取决于具体的数据库系统）。标准 SQL
不像常规外键那样直接内置支持强制多态外键约束。
